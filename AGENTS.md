# AGENTS.md — правила для AI-агентов

Проект: **1537paperstreet**, Markdown-ридер для macOS на Rust.
Читать перед началом любой задачи. Вместе с `PLAN.md` (архитектура) и `CHECKLIST.md` (задачи).

---

## 1. Порядок работы над задачей

1. Взять задачу из `CHECKLIST.md`. Проверить, что все зависимости `(← T-xxx)` закрыты.
2. Прочитать соответствующий раздел `PLAN.md`. Если задача противоречит плану — **остановиться и спросить**, не решать самостоятельно.
3. Ветка: `task/T-042-fsops-resolve`.
4. Сначала тест, потом код. Для задач, помеченных 🔒, тест обязателен до реализации.
5. Пометить задачу `[~]` в `CHECKLIST.md` при старте, `[x]` — в PR, который её закрывает.
6. PR закрывает **ровно одну** задачу.

---

## 2. Definition of Done

Задача не закрыта, пока не выполнено всё:

- [ ] `cargo fmt --all --check` — чисто
- [ ] `cargo clippy --workspace --all-targets -- -D warnings` — ноль предупреждений
- [ ] `cargo test --workspace` — зелёный
- [ ] `npm run lint && npm run test` — зелёный
- [ ] Публичные элементы задокументированы (`missing_docs` не срабатывает)
- [ ] Критерии приёмки из текста задачи выполнены и проверены
- [ ] Если задача влияет на производительность — замер приложен к PR
- [ ] Если задача трогает запись файлов — round-trip-тест «открыл и сохранил без правок ⇒ файл побайтово не изменился» проходит
- [ ] Если задача добавляет разрушительную операцию — снимок `pre_*` сделан до неё, и на это есть тест
- [ ] Если поменялся публичный API или поведение — обновлены `CHANGELOG.md` и затронутые доки
- [ ] Если принято архитектурное решение — добавлен ADR в `docs/adr/`

## 3. Правила для Rust-кода

**Запрещено:**

- `unwrap()`, `expect()`, `panic!` в библиотечном коде (`ps-core`, `ps-render`). В тестах — можно.
- Блокирующий I/O в потоке команд Tauri — только через `spawn_blocking`.
- Работа с путями в обход `fsops::resolve`. Это единственная дверь в файловую систему.
- Новая зависимость без обоснования в PR-описании. Правило: одна зависимость — одна ясная причина.
- `unsafe` без комментария `// SAFETY:` и одобрения в ревью.

**Обязательно:**

- Ошибки — через `thiserror`, единый тип на крейт. Сообщения об ошибках пишутся для пользователя, а не для разработчика.
- Любая запись в файл пользователя — атомарная: temp в той же директории → `fsync` → `rename`. Прямая запись поверх существующего файла запрещена без исключений.
- Любая операция, которая может уничтожить пользовательский текст, сначала делает снимок в историю. Девять точек перечислены в `PLAN.md` § 10.3 — новая разрушительная операция означает десятую точку, а не исключение.
- Перед записью документа сверяется `base_hash`. Расхождение = конфликт, а не повод перезаписать.
- `ps-core` и `ps-render` не импортируют `tauri`. Никогда. Это проверяется в CI.
- Команды в `ps-app` — тонкие: распаковать аргументы, вызвать core, вернуть. Если в команде появилась логика — её место в core.
- Тесты файловой системы — только на `tempfile`. Никаких обращений к реальному `$HOME`.
- Публичные типы, пересекающие IPC-границу, экспортируются в TypeScript через генератор. Ручное дублирование типов — ошибка ревью.

## 4. Правила для фронтенда

- UI ничего не вычисляет. Форматирование, сортировка, фильтрация, парсинг — в Rust.
- Никаких CSS-in-JS и UI-фреймворков поверх Svelte. Только CSS-переменные и обычный CSS.
- Цвета берутся **только** из токенов темы. Ни одного хардкоженного hex-значения в компонентах.
- Списки длиннее 100 элементов — обязательно виртуализированы.
- Единственное исключение из правила «логика в Rust» — текстовый буфер редактора: он живёт в CodeMirror (ADR-008). Всё остальное, включая рендер Markdown и любые операции с путями, остаётся в Rust.
- Ошибки IPC обрабатываются и показываются пользователю. Молчаливый `catch {}` — ошибка ревью.
- Никаких сетевых запросов. Все ассеты — локальные.

## 5. Производительность

Каждый PR, затрагивающий горячий путь (старт, открытие документа, скролл, поиск, дерево), должен содержать замер до/после.

Горячие пути и их бюджеты — в `PLAN.md` § 1.2. CI автоматически ловит регресс > 10 % относительно `benches/baseline.json`.

Если задача требует превысить бюджет — это не повод превысить бюджет. Это повод открыть обсуждение.

---

## 6. Безопасность и сохранность данных

**Главное правило проекта: пользовательский текст не теряется. Никогда, ни при каких обстоятельствах.**
Любой PR, затрагивающий `docio`, `drafts`, `history` или автосохранение, требует теста на потерю данных — не «теста, что работает», а теста на сценарий сбоя.

- Пользовательский Markdown — **недоверенный ввод**. Санитайзинг обязателен, если `allow_raw_html` выключен.
- Любой путь из UI проверяется на выход за корень проекта на стороне Rust. Проверка во фронтенде не считается проверкой.
- `asset://` scope ограничен корнями зарегистрированных проектов.
- Секреты и сертификаты — только в GitHub Secrets.
- Ноль исходящих запросов, кроме опциональной проверки обновлений.

## 7. Стиль

- Код, комментарии, имена, коммиты, ADR — **на английском**.
- `PLAN.md`, `CHECKLIST.md`, `AGENTS.md`, пользовательская документация — **на русском**; интерфейс приложения — на английском (локализация в бэклоге).
- Коммиты — Conventional Commits: `feat(core): add atomic json store`.
- Имена: `snake_case` в Rust, `camelCase` в TS, `kebab-case` для файлов CSS и Svelte-компонентов в `PascalCase`.

---

## 8. Когда остановиться и спросить

Не додумывать. Остановиться и задать вопрос, если:

- Задача противоречит `PLAN.md`.
- Требуется новая зависимость больше ~500 KB.
- Требуется изменить схему `projects.json` или `config.json`.
- Требуется изменить что-либо в пути записи файлов (`docio`, `drafts`, `history`, автосохранение) способом, не описанным в `PLAN.md` § 9.3 и § 10.
- Появляется желание завести счётчики ссылок в хранилище истории вместо mark-and-sweep.
- Инкрементальный рендер расходится с полным, и есть искушение «просто подправить ожидаемое значение теста».
- Требуется добавить сетевой запрос.
- Бюджет производительности недостижим выбранным подходом.
- Задача выглядит так, будто её нужно разбить на несколько.
- Обнаружена проблема безопасности.

Лучше один вопрос, чем один тихо сломанный инвариант.

## 9. Что не делать по своей инициативе

Список из `PLAN.md` § 18 — не входит в v1. Если возникло желание «заодно добавить редактирование» или «раз уж мы тут, сделаем экспорт в PDF» — не надо. Это отдельные задачи в бэклоге, и они там намеренно.
